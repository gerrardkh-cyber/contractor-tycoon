### 판정별
1. **크레인**: 지브 높이 = 계획 지붕 + 1.5층(그림 마스트는 칸 수 올림). 마스트는 건물 오른쪽에 건물 폭 0.15 간격.

2. 벡터 크레인 변경 — 승인대로 유지. (1·8의 높이·간격·기초 규칙은 벡터 모드에도 똑같이 적용했습니다.)
3. 가설사무소 높이 = 작업자 키 × 1.5. 걷는 폭(2.4)·대피 거리(4)·작업자 간격 여백(2)·검사관이 서는 곳(1.6)과 걸어오는 거리(15)를
   모두 **작업자 키 단위** 토큰으로(`theme.scene.*People`). 벡터 모드에선 키 9 기준이라 검사관 출발점은 전과 같습니다.
4. 환호·앉기: 그 자리에 멈춤(애니메이션 일시정지, 튀지 않음). 걷기·달리기·짐 나르기는 이동.
5. 펀치 처리: 짐 나르기 포즈로 층 위를 오갑니다.
6. 카메라 위 여백 = HUD `getBoundingClientRect().bottom` + 8px(`hudClearPx`). 창 크기 변경·회전·HUD 크기 변화(언어, 안내 여백)마다
   `ResizeObserver` 로 다시 잽니다.
7. **베이**: 층 타일의 기둥을 찾아(4개 → **3베이**) 기둥 중심에서 잘라 잇습니다. 주택·보수 2베이(양 끝 베이),
   저층 4베이(첫 베이 + 가운데 베이 ×2 + 끝 베이), 중층 타일 전체. 기초·지붕은 같은 폭으로, 양 끝을 살려 잘라 맞춤.
8. 기초 = 층 높이 × 0.4.

| 슬롯 상태 | 표시 |
|---|---|
| 보유 + 비어 있음 | `Empty lot` / "Ready for the next job" |
| 다음에 살 수 있는 칸 | `Next site` + 가격, `Buy slot $60,000` (현금 부족이면 비활성 + **부족액**) |
| 그 다음 칸 | `Next site` + 가격, 흐리게 + "Opens once site 2 is yours" |

매 프레임 다시 그리지 않도록 슬롯 키에 부족액을 **1,000 단위로 반올림**해 넣었습니다.

### 4. 사운드 볼륨 `0.4` 고정

`theme.soundVolume = 0.4`, `sound.ts` 가 `Audio` 를 만들 때 적용합니다.
소리 자체는 발주서 지시대로 **그대로 뒀습니다** — 여전히 파일명으로 고른 것이고 귀로 확인하지 못했습니다.

### 구현 중 잡은 것 3건

**1. 시드 의존 테스트 2건이 깨졌습니다.**
다양성 구현이 난수를 **3회 뽑기(타입·성향·검사관) → 1회 뽑기(조합)** 로 바꾸면서 시드 스트림이 이동했습니다.
규칙 계산이 틀린 게 아니라, 두 테스트가 특정 시드의 우연에 기대고 있었습니다.

| 테스트 | 실제 원인 | 수정 |
|---|---|---|
| `contract-basis` — 유보금이 P 기준이 아님 | 헬퍼 `awardProject` 가 **지명 계약**(fair 고정)을 잡아 요청한 `high` tier가 무시됨 → `awarded == contractBase` 가 되어 단언이 무의미해짐 | 헬퍼가 `fair` 가 아닌 tier를 요청하면 `directAward` RFQ를 건너뛰도록 |
| `cash-floor` — 수리 대금 전액 즉시 입금 | `change_order` 가 터져 계약금이 1.1배(3,000 → 3,300)가 됐는데, 테스트는 **입찰 직후** 금액을 비교 | 진행 중 계약금을 추적해 **정산된 금액**과 비교 |

**2. 힌트가 두 장에 겹쳐 보였습니다(004 회귀).**
카드가 교체될 때 나가는 카드가 `is-leaving` 으로 200ms 남는데, 힌트를 그대로 들고 있어
새 카드가 힌트를 받는 같은 프레임에 **같은 줄이 두 번** 보였습니다. 나갈 때 힌트를 떼도록 고쳤습니다.

**3. 슬롯 카드에 안쪽 여백이 없었습니다.**
`Next site` 와 가격이 카드 테두리에 붙었습니다. `.empty-lot` 에 패딩을 넣었습니다.

## balance-sim 3차 — **생명줄에 구현 버그. 잠금이 조건부로만 닫혔습니다 (BLOCKER)**

### 발견한 버그 — `canAffordBid`가 음수 잔고에서 생명줄을 막는다

```ts
// src/core/rfq.ts
export function canAffordBid(state, rfq) {
  return state.company.cash >= rfq.minCash;   // 생명줄은 minCash = 0
}
```

생명줄의 `minCash`가 `0`이므로 이 검사는 **`cash >= 0`** 이 됩니다. 현금이 **−$1만 되어도** 생명줄이 게시판에 떠 있는데 입찰이 거부됩니다(`cash below the bid minimum`). 현장이 0이면 수입 경로가 없어 **잔고가 그 값에 영구 동결**됩니다.

| `−$1` | ✅ | ❌ | ❌ | **`true`** |
| `−$17,144` | ✅ | ❌ | ❌ | **`true`** |

## 새 병목 — 펀치리스트 비용이 층수에 비례해 폭발합니다

`펀치 비용 / P = 평균 minor × 게이트 인스턴스 수 × 0.003`

| 타입 | 게이트 수 | lenient | normal | **strict** |
|---|---|---|---|---|
| `house` | 6 | 0.9% | 3.6% | **8.1%** |
| `lowrise` | 10 | 1.5% | 6.0% | **13.5%** |
| `midrise` | **20** | 3.0% | **12.0%** | **27.0%** |

**게이트 수가 층수에 비례해 늘어나는데 minor 개수는 게이트마다 굴립니다.** midrise는 `1 + 8 + 8 + 1 + 2 = 20`개 게이트라, strict에서 평균 4.5개 × 20 = **90개 minor**가 쌓이고 정리비가 계약액의 **27%** 가 됩니다. midrise/strict의 −28% 적자에서 재작업비(−13%)보다 **펀치 정리비가 더 큰 항목**입니다.

이건 지시 4번(strict minor `2~4 → 3~6`, normal `1~2 → 1~3`)의 직접적 결과입니다. strict의 통과율을 올려 재작업비는 줄였는데, **minor를 늘려 펀치 비용이 그보다 크게 늘었습니다.**

## 근본 원인 — 입찰 문턱과 바로 다음 착수비의 2.33배 격차

| 타입 | 검사관 | `min_cash` (foundation) | 다음 `structural` 착수비 | 배수 |
|---|---|---|---|---|

### 생명줄이 그 격차를 못 메웁니다

`$2,000 / 90초` (60초 작업 + 30초 쿨다운):

| 목표 | 필요 횟수 | 소요 |
|---|---|---|
| `$19,125` (house 입찰선) | 10회 | **15분** |
| `$44,625` (structural 착수) | 23회 | **35분** |
| `$63,750` (foundation + structural) | 32회 | **48분** |

4차에서는 `$10,000 / 60초`라 같은 격차를 **4분 30초**에 메웠습니다. 수입을 1/5로, 주기를 1.5배로 바꾸면서 **회복 속도가 7.5배 느려졌습니다.**

### 제 판단 — 두 결정이 겹쳐 생긴 구조입니다

1. **`min_cash`를 foundation만으로 축소(2차 제안 1-c)** — 당시에는 `min_cash` 하한선 자체가 데드락 원인이라 낮춘 것이었습니다. 그 결과 **감당 못 하는 일을 집을 수 있게** 되었습니다.
2. **생명줄 인하** — 격차를 메우던 다리가 사라졌습니다.

**중요한 것은, 1번을 되돌려도 이제는 안전하다는 점입니다.** `min_cash` 하한선이 데드락이었던 이유는 그 밑에서 빠져나올 방법이 없었기 때문인데, 지금은 **생명줄 + 현금 하한 0 + 부채**가 그 역할을 합니다. `minCashStages`에 `structural`을 다시 넣으면:

- house/lenient `$63,750` < 시작 자본 `$80,000` → 입찰 가능
- house/strict `$82,875` > `$80,000` → **위험한 건은 자동으로 걸러짐**
- lowrise `$136,000` → 초반 차단
- **감당 못 할 일을 애초에 집지 않으므로 바닥까지 떨어지는 빈도 자체가 급감**

### 확장 — 여전히 안 열림

슬롯2(2~3.6h) → **3~4시간 공백** → 면허2(5.5~7.35h, fair만) → 끝. 슬롯3은 전 런 미해금.

현재 언락 대상이 **슬롯2·슬롯3·면허2 세 개뿐**입니다(면허3 이상은 데이터에 없음). "30분마다 뭔가 열린다"는 밸런스 수치 문제가 아니라 **콘텐츠 개수 문제**입니다.

### 8시간 방치 평가

**유의미한 진행을 만듭니다.** 준공 62~91건, 슬롯2 전 런 해금, fair는 면허2·lowrise까지 도달. 자금 곡선도 $1,408 → $140,673처럼 30분 단위로 크게 출렁입니다. 다만 **면허2 이후 진행은 사실상 없습니다.**

### sim 정책 주의

정책이 여윳돈을 즉시 슬롯·협력사에 재투자하도록 되어 있어(제 지시) **현금을 일부러 얇게 굴립니다.** 생명줄 의존도에 이 영향이 섞여 있습니다 — 더 보수적인 정책이었다면 빈도가 낮았을 것입니다. 또한 에이전트가 예비금 계산 버그를 중간에 발견해 고치고 전체를 재실행했습니다(위 수치는 수정 후).

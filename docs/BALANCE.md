## 0. 해석 결정 — **A~G 전부 승인 확정**

발주서 문구가 두 가지로 읽히던 지점들입니다. **전부 지시로 승인 확정되었으므로 이제 규칙입니다.**

| # | 지점 | 발주서 문구 | **확정 규칙** | 이유 |
|---|---|---|---|---|
| A | 공정 cost/pay 비율 | "cost(P비율)" 합계 1.00 vs "공사비 = 0.85P 고정" | **배분 비율**. cost 비율은 총공사비(0.85P)의 배분, pay 비율은 낙찰금액의 배분 | P 비율로 읽으면 공사비=1.00P → fair 마진 0, low 확정 손실 |
| B | 협력업체 검사 보정 | §5 "Lv×1.5%" vs §6 "1.5%×(Lv−1)" | **(Lv−1)×1.5%** | §6과 시간 배율 `0.92^(Lv−1)`이 모두 Lv1=무보정. 검사관 기본값 85/70/50%가 Lv1 실측 통과율이 됨 |
| C | 수의계약 | "입찰 없이 fair 낙찰" | RFQ에 `directAward` 플래그. **fair 단일 선택지, 낙찰 100%**. 자동 수주는 아님 | 자동 수주는 현장 상한 초과 시 처리 불가 |
| D | change_order 발동 시점 | "프로젝트당 1회 25%" | 프로젝트 시작 시 1회 판정, 적중 시 **예상 공기 내 균등 랜덤 시점**에 발동 | "진행 중 단계 시간 +20%"가 중간 발동을 전제 |
| E | rain 범위 | "60초마다 15%" | **회사 전역 1개 기상 이벤트**, `pending_decision`은 **현장별** | 날씨는 지역 단위, 타설 강행은 현장 판단 |
| F | material_spike 범위 | "다음 시작 단계 비용 +15%" | **전역 1회성**. 다음에 시작하는 단계 1개에만 적용 후 소멸 | 자재 시세는 회사 전역 |
| G | 열린 minor 신뢰도 감점 | "5개당 −1(프로젝트 종료 시 정산)" | **문자 그대로 종료 시점 열린 개수 기준** | 아래 §5.4 주 참조 — v1에서는 상시 0 |

## 3. 공정

`src/data/process-stages.json` — 협력업체 Lv1 기준

| stage | 담당 협력업체 | 기본 시간 | cost 배분 | pay 배분 | 지급 시점 |
|---|---|---|---|---|---|
| `foundation` | sitework | `40s` | `0.15` | `0.15` | foundation 게이트 통과 |
| `structural` (층당) | structure | `60s` | `0.35 / floors` | `0.35 / floors` | **해당 층 structural 게이트 통과** |
| `mep` (층당) | electrical + plumbing + fire | `45s` | `0.25 / floors` | `0.25 / floors` | **해당 층 mep 게이트 통과** |
| `weatherproof` | structure | `30s` | `0.10` | `0.10` | weatherproof 게이트 통과 |
| `final` | fire → 전체 | `30s` | `0.15` | `0.15` | final 게이트 통과 → CO |

### 3.0 기준액 (승인 확정)

| 비율 | 곱하는 기준액 | 값 |
|---|---|---|
| **cost 배분** | **총공사비** | `0.85 × P` — 견적 티어와 무관하게 **고정** |
| **pay 배분** | **낙찰금액** | `P × 티어 배율` (change_order 적용 시 그 값) |

- cost 배분 합 = `1.00` → 지출 총액 = **`0.85 × P`**
- pay 배분 합 = `1.00` → 수입 총액 = **낙찰금액 전액**
- **낙찰금액이 움직여도 공사비는 움직이지 않는다.** 티어 선택도, change_order도 `0.85 × P`를 건드리지 않는다.
- **기성은 각 공정이 자기 게이트를 통과할 때 자기 몫을 받는다.** 층 공정도 `structural` `0.35/floors` 와 `mep` `0.25/floors` 로 나뉘어 각자 지급된다.

### 3.1 층 파이프라인

```
structural n 완료 → [structural 게이트 n] → 통과 시:
                                             mep n 시작
                                             structural n+1 시작
mep n 완료 → [mep 게이트 n] → 통과 시 mep 몫 지급
```

층 기성은 두 몫으로 나뉘어 **각 게이트 통과 시점에 각각** 지급된다.

- `mep n` 은 `structural n` 이 **검사 통과**해야 시작한다.
- `structural n` 미통과 시 `structural n+1` 도 진입 불가.
- 전 층 mep 통과 후 `weatherproof` 진입.

### 3.2 비용·정지

- 단계 **비용은 시작 시 차감**한다.
- 잔고 부족이면 단계를 시작하지 않고 **대기**, 현장은 `stalled` 표시.

### 3.3 예상 공기 유도 (Lv1, 무실패)

```
foundation 40
structural  60 × floors        (직렬 체인)
mep 마지막 층 45               (앞 층 mep는 structural에 가려짐: 45 < 60)
weatherproof 30
final 30
────────────────────────────
합계 = 145 + 60 × floors
```

### 3.4 기한 초과

| 항목 | 값 |
|---|---|
| deadline 초과 시 신뢰도 | `−10` |
| `schedule` 성향 추가 페널티 | **최종 기성(`final` 단계 지급액) `−10%`** |

## 4. 입찰

### 4.1 게시판

| 항목 | 값 |
|---|---|
| 슬롯 수 | `3` |
| 교체 주기 | `90s` 마다 **가장 오래된 1칸** |
| 낙찰·거절 시 | 해당 칸 **즉시 교체** |

RFQ 필드: `type`, `P`(성향·검사관 보정 후), `client_trait`, `inspector`, `deadline_sec`, `advance_available`, `min_cash`

### 4.1.1 입찰 자격 (`min_cash`)

```
min_cash = foundation 비용 + structural 1개 층 비용
         = 0.85P × 0.15  +  (0.85P × 0.35) / floors
```

- **현금 `≥ min_cash` 일 때만 그 RFQ에 입찰할 수 있다.**
- 미달이어도 **RFQ는 게시판에 그대로 남는다.** 입찰만 막힌다(`입찰 불가` 상태).
- 기성이 한 푼도 들어오지 않는 첫 구간을 자기 돈으로 덮을 수 있는지만 본다.

| 타입 | P (lenient 기준) | `min_cash` |
|---|---|---|
| `house` | `$150,000` | **`$63,750`** |
| `lowrise` | `$600,000` | **`$136,000`** |
| `midrise` | `$2,000,000` | **`$329,375`** |

시작 자본 `$80,000` 기준: `house` 입찰 가능, `lowrise`·`midrise` 불가.

### 4.2 견적 3단계

| 단계 | 낙찰금액 | 기본 낙찰 확률 |
|---|---|---|
| `low` | `0.90 × P` | `80%` |
| `fair` | `1.00 × P` | `50%` |
| `high` | `1.15 × P` | `20%` |

- 총공사비 `0.85 × P` 고정
- 마진: low `0.05P` / fair `0.15P` / high `0.30P`

### 4.3 발주처 성향 (`client_trait`)

| trait | 효과 |
|---|---|
| `price` | low 낙찰 확률 `+10%p`, high `−10%p` |
| `track` | 신뢰도 `≥70` 이면 3단계 전부 `+15%p` |
| `schedule` | `deadline × 0.8`, 기한 초과 시 최종 기성 `−10%` |

분포: 균등 `1/3` 씩.

### 4.4 검사관 (`inspector`)

| inspector | 기본 통과율 | 통과 시 minor | P 배율 | 출현 확률 |
|---|---|---|---|---|
| `lenient` | `85%` | `0~1` | `×1.00` | `40%` |
| `normal` | `70%` | `1~2` | `×1.05` | `40%` |
| `strict` | `50%` | `2~4` | `×1.15` | `20%` |

`P_rfq = P_base × inspector 배율`. 이후 모든 `P×` 수치는 `P_rfq` 기준.

### 4.5 구제 장치

| 항목 | 값 |
|---|---|
| 연속 낙찰 실패 | `3`회 → 다음 RFQ `1`건 **지명** (낙찰 `100%`, `fair` 고정) |
| 수의계약 | 신뢰도 `≥70` 일 때 **새 RFQ의 `10%`** 가 `directAward` (`fair` 고정, 낙찰 `100%`) |
| 연속 실패 카운터 리셋 | 낙찰 성공 시 `0` |

### 4.6 선수금 (advance)

| 항목 | 값 |
|---|---|
| `advance_available` 조건 | **플레이어 신뢰도 `≥60`** |
| 지급 | 낙찰 즉시 `P × 0.10` 입금 |
| 회수 | 매 기성에서 `기성액 × 10%` 차감, 잔액 0까지 |

## 6.1 프로젝트 포기 (Abandon)

**언제든 가능하다.** 조건 없음.

| 항목 | 처리 |
|---|---|
| 유보금 | **전액 몰수** (한 푼도 돌려받지 못한다) |
| 선수금 미회수 잔액 | **즉시 전액 반환** |
| 현금 부족 시 | **음수 잔고 허용.** 다음 수입에서 우선 차감된다 |
| 신뢰도 | **`−15`** |
| 현장 슬롯 | **즉시 해제** |
| 기록 | 포기 기록만 남는다. **준공 건수에 포함되지 않고, 하자 기간도 열리지 않는다** |
| 지연 중이던 기성 | **회수하지 않는다** — 이미 게이트를 통과해 확정된 기성이므로 예정대로 입금된다 |

- 음수 잔고 동안에는 모든 단계 착수와 펀치 정리가 정지한다(잔고 부족 판정과 동일).
- **긴급 대출은 미구현.** 회복 경로는 포기와 다른 현장의 수입뿐이다.

## 8. 기성 / 유보금 / 선수금

지급 계산 순서:

```
gross      = pay배분 × 낙찰금액                  ← 기준은 pay(낙찰금액), 공사비나 P가 아니다
retainage  = gross × 10%                        → 유보, CO 시 일괄 지급
advanceDed = min(gross × 10%, 선수금 잔액)       → 선수금 회수
net        = gross − retainage − advanceDed     → 입금
```

**유보금·선수금 차감은 전부 `gross`(pay 기준)에서 계산한다** (승인 확정).
따라서 change_order로 낙찰금액이 오르면 그 이후 기성의 유보금·선수금 차감액도 같은 비율로 커진다.

| 항목 | 값 |
|---|---|
| 유보율 | `10%` |
| 유보금 지급 | CO 시 일괄 |
| 선수금 회수율 | 기성액의 `10%` |
| `schedule` 성향 지연 시 | **최종 기성 `× 0.90`** |

## 9. 이벤트

`src/data/event-templates.json`

| id | 발동 | 효과 |
|---|---|---|
| `rain` | `60s` 주기, `15%` | 지속 `30~60s`. `foundation`·`structural` **정지**. 선택지 `risky_pour`: 진행하되 해당 층 structural 검사 `−20%` |
| `material_spike` | `60s` 주기, `10%` | **다음에 시작하는 단계 1개** 비용 `+15%` (전역 1회성) |
| `strict_inspector` | 프로젝트 시작 시 `20%` | 그 프로젝트 **전 검사 `−10%`** |
| `payment_delay` | 기성 발생 시 `15%` (`schedule` 성향 `30%`) | 입금 `60s` 지연 |
| `change_order` | 프로젝트당 `1`회 `25%` | **발동 시점 이후 잔여 기성에 `+10%`. 공사비 `0.85P`는 불변.** 발동 시점 진행 중 단계 잔여 시간 `+20%` |

- 선택형 이벤트(`rain`)는 상태에 `pending_decision` 으로 **노출만** 한다. core 는 판단하지 않는다.
- 오프라인·미응답 시 **기본값 = 대기**(정지).

### 9.1 change_order 기준 (확정)

`+10%` 는 **발동 시점 이후 잔여 기성에만** 붙는다. **소급하지 않는다.**
공사비 `0.85 × P` 는 변하지 않으므로 **증액분은 전액 마진**이다.

| 대상 | change_order 후 |
|---|---|
| 낙찰금액 (`awarded`) | `× 1.10` |
| 총공사비 (`0.85 × P`) | **불변** |
| 단계별 cost | **불변** |
| **이미 지급된 기성** | **불변 (소급 없음)** |
| 발동 이후 잔여 기성 | `× 1.10` |
| 유보금 차감 | `× 1.10` (pay 기준이므로) |
| 선수금 차감 | `× 1.10` (pay 기준이므로) |

지급 완료 비율이 `s` 일 때 프로젝트 총 수입은 `낙찰금액 × (1.10 − 0.10 × s)` 가 된다.
**이는 의도된 결과다** — 이미 청구가 끝난 기성은 다시 열지 않는다.
